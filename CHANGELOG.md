# Changelog

All notable changes to `pushery/http-api-for-laravel` are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), and the project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

A release carries only the sections that have an entry, in this order: `### ⚠️ Breaking`, `### ✨ Added`, `### 🔧 Changed`, `### ⚡ Performance`, `### 🐛 Fixed`, `### 🔒 Security`, `### 🧹 Deprecated`, `### 🗑️ Removed` and `### 📚 Documentation`.

## [0.3.0] - 2026-11-20

### ✨ Added

- **A document the package writes itself is titled in the locale of the application and names its language.** The title of its status comes from the package's catalogs in English, German, Spanish, French, Italian, Dutch and Portuguese, and `Content-Language` names the language the title and the detail are written in. A regional locale reads the catalog of its language, and a locale without a catalog is answered in English. Neither Laravel nor the package sets the locale from `Accept-Language`: the page of the problem documents shows the middleware an application adds to answer each client in its language.
- **The application names the documents the package writes itself.** `NamesProblems`, where an application binds it, receives each document the package writes for a validation, a missing authentication, an HTTP exception or an exception nobody anticipated, together with the failure, and returns the answer with the application's own `type`, `title` and members such as a stable `code`. A problem an exception provides through `ProvidesProblem` does not pass through it, and without a binding every document stays as it was.
- **`PruneExpiredIdempotencyKeys` deletes the expired keys from a database or a file store.** Both stores delete an expired key only when that key is read again, and a client sends every new request under a new key, so the rows or files of past keys stayed for good, each with the answer it kept. Scheduled once a day with `Schedule::call(PruneExpiredIdempotencyKeys::class)->daily()`, it deletes the row of every expired key from the table of the store the keys are kept in, a thousand rows to a statement, or every expired file under the directory of a file store, and does nothing on any other store. A file store names a file by the hash of its key, so there the expired file of any key goes, which the store already treats as missing.

### 🐛 Fixed

- **The problems of the idempotency middleware name the header the API reads.** With `http-api.idempotency.header` set to another name, such as `X-Idempotency-Key`, every one of them still asked for an `Idempotency-Key` header, which the middleware did not read, so a client that followed the advice was refused again. Their details name the configured header now, in every catalog, and the German titles name the idempotency key as the other languages do, `Idempotenzschlüssel fehlt` in place of `Idempotency-Key fehlt`. The setting and `max_key_length` are documented in the configuration file and on the idempotency page. **Upgrade:** a catalog published under `lang/vendor/http-api` keeps its own lines; write `:header` where one of them names the header.
- **A `QUERY` request passes the idempotency middleware untouched, as a `GET` does.** The middleware kept its own list of safe methods, and `QUERY` was missing from it: a search sent with a key took the key, its answer was replayed, and the next search under the same key with another body was refused with `422`. It asks the request now, so every method HTTP calls safe passes: `GET`, `HEAD`, `OPTIONS`, `TRACE` and `QUERY`.
- **An answer whose body is no valid UTF-8 is replayed from a database store.** The database store writes the record into a text column, which PostgreSQL and MySQL refuse for such bytes, so an answer in Windows-1252, for one, was never kept there: the failure was reported on every such write, and every repeat was answered with `409`. The middleware keeps such a body as base64 now, a third larger, and replays it byte for byte. A body in UTF-8 is kept as it was.
- **A store that refuses to keep an answer is reported, as one that throws on the write is.** memcached refuses an item above its item size by returning false rather than throwing, and every repeat of such a request was answered with `409` while the application's error reporting heard nothing of it. A refusal is reported now as an `AnswerNotKept` that names the store and the size of the body it was to keep.
- **A store that takes no key is answered with `503` and reported, not with the `409` of a request nobody runs.** A Redis under `noeviction` that has filled up refuses every write, through phpredis without an exception, and the middleware read that as a key another request held: every write under a key was answered with `409` and asked to be sent again, and nothing was reported. Such a request is answered with `503` now, with `Retry-After: 30` and the problem type `idempotency-key-not-taken`, in every catalog, and does not act, and a `KeyNotTaken` that names the store is reported. A record found under the key is answered with `409` as before.
- **Under Laravel Octane, the problem documents follow the configuration of the request.** The renderer the package hands the exception handler read its switches and settings from the application the package was booted with, while Octane runs each request with a configuration of its own, so a value set for a request, `http-api.problems.enabled` or `http-api.problems.hosts` for one, never reached its documents. They are read from the configuration of the request now, as the idempotency middleware reads its own.
- **A refused request keeps its own answer when the store throws while its key is freed.** The middleware frees the key of an answer of `400` or more, and a store that threw on that, a Redis that could not be reached for one, replaced the route's answer, the `422` of a validation for one, with a `500`. The failure is reported now and the client gets the route's answer. The key stays taken until `in_flight_ttl` runs out, so until then a repeat is answered with `409` and the corrected request with `422`.
- **A key with a line feed at its end, inside its quotes, is refused as malformed.** The middleware trims the header before it takes the quotes off a structured-field string, so a line feed inside the quotes stayed in the key, and the check for printable ASCII let it through: its pattern ended on `$`, which also matches before a final line feed. Such a key is answered with the problem document of a malformed key now, as any other character outside printable ASCII is.

### 🗑️ Removed

- **`Support\TableLookup` and `Support\MigrationLocks` are no longer shipped.** Both are helpers for the migrations of a package, and this one ships no migration and looks up no table, so nothing in it called either. The provider no longer loads a routes file, since the package registers no route of its own. **Upgrade:** an application that calls one of the two classes copies it from the 0.2.0 release into its own namespace.

### 📚 Documentation

- **The advice on the store for the keys names the condition that decides.** It is a store every process and server of the API shares and that outlasts the request: redis, database or dynamodb, and the file store where a single server answers the API. The array store, which forgets its keys with the request, is no longer named as one, and the file store is no longer said to lack an atomic `add()`, which Laravel's keeps.
- **The advice names every way a store loses a key before `ttl`.** Beside eviction, which memcached does too unless it runs with `-M`, a key goes when `cache:clear` or `optimize:clear` flushes its store, a Redis store with the whole database of its connection, and when the store restarts without persistence. The keys belong in a store of their own, a Redis connection and database no other store uses, with `noeviction` and `appendonly yes`, or a database store with a table of its own, and memcached is no longer recommended.
- **The idempotency page warns that a kept answer lies unencrypted in the store.** An answer is kept as it was sent, body and headers, for `ttl`, so whoever can read the store, a backup of its database or a shared Redis, reads it there. A route whose answer carries a secret the client sees only once, such as a new API token or recovery codes, does not take the middleware, unless the store is guarded like the database itself.
- **The start page shows the package at work.** An order sent a second time under its `Idempotency-Key` gets the first answer back, marked `Idempotent-Replayed: true`, and an order the API refuses is answered as a problem document. Both requests and their answers stand under the picture as text too, where a reader can enlarge, search and copy them.
- **The advice warns against a store of the `failover` driver.** When one of its stores throws, a Redis that cannot be reached for one, it takes the keys in the next store, which never saw the keys taken before, so a repeat acts a second time, and once the chain reaches `array`, every repeat does. The idempotency page, the configuration file and the Boost skill name a single store for the keys.
- **The examples of a route run where they are pasted.** They wrote `/api` into the path and named no file, and in `routes/api.php`, where Laravel puts `/api` in front of every path, such a route answers `/api/api/orders`. They name the file now and write the path as it stands there. The example of the `optional` parameter authenticates the request first, as every route with the middleware has to, the resolver of a scope declares its namespace and names its file, `app/Http/ApiKeyScope.php`, and the idempotency page and the page of the problem documents say where a binding goes: the `register` method of a service provider.
- **The documentation says that a request expecting JSON gets a problem document on every route.** The installation named only requests under `/api`, while a request that expects JSON gets one on any route, a form a page sends from its own scripts to a web route among them, and so does a request that asks for `application/problem+json`, in place of Laravel's own JSON and its `message`. The start page names all three, and the page of the problem documents, the configuration file, the README and the Boost skill name `http-api.problems.when_json_is_expected`, which set to `false` keeps Laravel's answer on the routes outside the API.
- **The README names the databases Laravel Cloud runs and claims no more.** Its requirements said the package was tested on PostgreSQL and MySQL 8.4 and concluded that it would run on Laravel Cloud without further setup. A run against a database server in a test lane is no run on Laravel Cloud's serverless Postgres, so the sentence keeps the fact and drops the conclusion.
- **The PHP examples import every class they name.** An example that opens with `use` lines is the head of a file a reader copies, and a class those lines leave out resolves in the namespace of that file: `extends RuntimeException` in a file under `namespace App\Exceptions;` asks for `App\Exceptions\RuntimeException`. The exception an application declares for itself on the problems page and in the Boost skill imports `RuntimeException` now, and the binding of `NamesProblems` imports `Throwable`.

## [0.2.0] - 2026-11-11

### ✨ Added

- **An API on a host of its own gets problem documents without a path prefix.** `http-api.problems.hosts` names the hosts whose every request belongs to the API, such as `api.example.com`, so a failure there is answered as `application/problem+json` without a prefix and without the request asking for JSON. An application whose routes know their API better binds its own `RecognizesApiRequests`, which the package then asks instead of the prefixes and the hosts.

### 🔧 Changed

- **The two switches read their rule from the package, so a fix to it reaches a published config.** `config/http-api.php` spelled out how a value of the `.env` turns them on or off, and a host that published the file kept that rule as it was on the day it published it, so a later fix to the rule, such as the one for an empty `.env` line, never reached the copy. The config calls `EnvSwitch::read()` now, and the rule ships in `src/Support/EnvSwitch.php`: `false`, `0`, `no` and `off` switch off, `true`, `1`, `yes` and `on` switch on, trimmed and in any case, and anything else keeps the value the package ships. **Upgrade:** in a published copy, replace the expression of each once with its call and import the class: `enabled` with `EnvSwitch::read(env('HTTP_API_ENABLED'), true)` and `problems.enabled` with `EnvSwitch::read(env('HTTP_API_PROBLEMS'), true)`, and `use Pushery\HttpApi\Support\EnvSwitch;` at the top.

### 🐛 Fixed

- **An empty `HTTP_API_ENABLED=` or `HTTP_API_PROBLEMS=` keeps the switch on.** An empty line, as copying a template of a `.env` leaves one, switched the package or its problem documents off without a word, while a missing line kept them on. Only `false`, `0`, `no` and `off` switch them off now, in any case and with spaces around them.

## [0.1.0] - 2026-11-08

### ✨ Added

- **`Idempotent`, the `Idempotency-Key` of draft-ietf-httpapi-idempotency-key-header for Laravel.** A write under a key acts once: a repeated request gets the first answer again with `Idempotent-Replayed: true`, the same key with another request is refused with `422`, a request while the first one runs with `409`, and a missing or malformed key on `POST` and `PATCH` with `400`. The request's fingerprint covers its method, path, query, body, form fields and files. Only an answer below `400` is kept, so a corrected request goes through under the same key. A key belongs to the scope `ResolvesIdempotencyScope` names, the signed-in user by default, and is taken for `in_flight_ttl` while its first request runs and kept for `ttl` afterwards. An answer the store cannot hold, and a streamed answer or a file download, still reaches the client, and its key stays used for `ttl`: a repeat is answered with `409` instead of acting a second time.
- **Problem documents, RFC 9457.** `Problem` answers as `application/problem+json`, and `ProblemRenderer` turns the failures of an API request into one: a validation into `422` with its `errors`, an unauthenticated request into `401` with the `WWW-Authenticate` header RFC 9110 requires, an HTTP exception into its status and headers with the message it was thrown with as `detail`, an exception implementing `ProvidesProblem` into its own document, and anything else into a `500` that says nothing about itself. A response an exception carries is kept as it is. A page that is no API page is left as Laravel renders it.
